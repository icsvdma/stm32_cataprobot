## 現行構成

```text
PS3 → ESP32 → SPI → STM32 → 左右モーター・ヘッドライト
         ↑              ↑
     Webモニター    ICM-20948 / BMP280
```

| 項目 | 仕様・実装の概要 |
|---|---|
| 操作 | 左Yで前後、右Xで旋回。ESP32が50 ms周期で左右指令を送信 |
| モーター | 20 kHz PWM、速度指令0〜1000、呼出しごとに最大50加減速 |
| SPI | Mode 0、1 MHz、XOR、応答padding 64 byte、ACK/NACK |
| センサー | 9軸100 Hz、温度・気圧10 Hzを目標にポーリング |
| 復旧 | 3回連続エラーで無効化、1秒間隔で再初期化 |
| 表示 | Version 2・32 byte、Web更新100 ms、受信から500 ms超でstale |

## 改善候補

優先度は暫定。発生頻度と実機への影響は未測定。

| 優先 | 問題・根拠 | 改善案 |
|---|---|---|
| 高 | SPIモーター指令の途絶を検出しない。ESP32切断時の停止送信は1回で結果を未確認。STM32メインループは通信断でもIWDGを更新する | STM32で有効なモーター指令の期限を監視。センサー要求で延命しない。停止送信失敗の扱いも定義 |
| 高 | 正転1000→通常停止→更新1回→逆転1000では、現在方向だけがBRAKEになり内部速度950が残る。反転判定を通らず高いPWMで逆転し得る | 停止を挟む場合も、前回の回転方向と出力ゼロからの時間で反転条件を判定する |
| 高 | SPIの解析済みフラグはメインループでのみ解除する。センサー復旧待ち中は、最初の取引後の別CS取引も解析されない可能性がある | フレーム境界の処理をメインループの進行から独立させ、復旧中も停止指令を受理する |
| 高 | 加減速が時間でなく呼出し回数に依存。同じループのセンサー再初期化には100 ms等の待ちがある | 加減速量を時間で定義し、制御周期・最大遅延を保証。センサー復旧を待ち状態へ分割 |
| 高 | SPI IRQをHブリッジ初期化前に有効化。起動途中の緊急停止・シャットダウンは未設定のタイマポインタを参照し得る | 出力と状態の初期化完了後に操作コマンドを受け付ける |
| 高 | SPI割り込みが、メインループで逐次更新中のセンサー値をコピーする。新旧の軸値・状態・時刻が混在し得る | 完成したスナップショットだけを短い排他区間等で公開する |
| 中 | 通常停止は内部速度を段階的に減らすが、出力方向は先にBRAKEへ変更され、両PWMは直ちに0になる | 「通常停止」の出力波形と停止時間を定義し、設計と実装を合わせる |
| 中 | 反転100 msの起点は反転検出時。ゼロ到達後100 msとは限らず、説明が資料・コメント間で一致しない | 反転検出からか、出力ゼロからかを決定し統一する |
| 中 | 緊急停止で駆動許可をLOWにするが、SPIには解除コマンドがない。その後の速度指令にもACKを返す | 停止保持・解除手順・停止中のコマンド応答を定義する |
| 中 | センサー群の取得周期は異なるが、応答時刻は1個。いずれかの更新で時刻とシーケンスが進む | 群別の有効期限を仕様へ明記。個別の取得時刻が必要か判断する |
| 低 | 要件定義の表紙は2.1、設計書は2.3だが履歴には3.0があり、設計書の2.3も重複 | 文書の版・更新日・適用範囲を統一する |

## 設計判断の分岐

```text
改善の優先順位【合意: 安全性と制御周期の保証を最優先】
├─ 通信断
│  ├─ 指令の有効期限
│  ├─ 停止方法と最大停止時間
│  └─ 復旧後の再始動条件
├─ 停止の意味
│  ├─ 通常停止の減速と出力波形
│  ├─ 緊急停止の保持・解除
│  └─ 回路上のブレーキと惰性停止の区別
├─ 時間保証
│  ├─ 加減速時間・最大制御遅延
│  └─ 反転100 msの起点
└─ データの意味
   ├─ スナップショットの整合性
   └─ センサー群別の鮮度
```

第1ラウンド: 通信断時の停止、停止後の再始動、制御周期の保証を最優先にする。ユーザー合意済み。

第2ラウンド（Q2〜Q5はユーザー合意済み。数値は実機検証前の設計値。未実装）:

- Q2: モーターA/Bを各々監視し、最後の有効な走行・通常停止指令から250 msで両輪の駆動出力を停止する。センサー要求・ライト操作・不正パケットでは期限を延長しない。250 msはESP32の50 ms送信周期の5周期分。
- Q3: 通信が復旧しても自動再始動せず、スティック中立を確認後、操作者の明示的な再開操作を必要とする。具体的な操作と緊急停止解除の扱いはQ6・Q7で合意した。
- Q4: 加減速を経過時間で定義し、通常の0→1000、1000→0のPWM指令変化を各500 msとする。実回転速度・停止時間とは区別する。異常時停止は通常減速を待たない。制御周期と許容遅延はQ8で合意した。
- Q5: 反転待ち100 msの起点をPWM出力ゼロへ統一し、通常停止を挟んでも逆方向への駆動まで待ち時間を満たす。機械的な停止を保証する時間とは扱わない。

回路資料の調査ではHブリッジの型番・回路図・メーカー真理値表を確認できなかった。`code_design.md:286–290` のLOW/LOWは「ブレーキ停止」と呼ばれるが、物理的な制動か惰性停止かは確定できない。100 msの実測・選定根拠も記載がない。上記の「駆動出力停止」は車体停止を意味しない。制動方式の決定は回路情報の確認後とする。

第3ラウンド（Q6〜Q9はユーザー合意済み。未実装）:

- Q6: 起動・PS3再接続・通信断復旧後は、操作に使う2軸の中立を300 ms連続で確認し、その後のSTART新規押下で走行を許可する。START長押しの継続では解除しない。中立は既存の `abs(ly)<20 && abs(rx)<20` を採用。タイマと入力状態は再接続時に破棄する。
- Q7: □の新規押下を緊急停止に割り当てる。緊急停止とシャットダウンは電源再投入まで保持し、STARTでは解除しない。現行アプリが参照する操作ボタンは▲のみであり、□・STARTのアプリ内用途は確認されなかった（関連ESP32 `src/main.cpp:239`）。
- Q8: STM32の制御更新は5 ms周期、最大更新間隔10 msを設計目標とする。指令期限250 msの経過後10 ms以内、すなわち最後の指令から260 ms以内に駆動出力をゼロにする。センサー故障・復旧中も同じ条件で検証する。
- Q9: 左右の走行指令を1つのSPIコマンドとして受信・検証し、同時に採用する。片輪だけを新しい指令へ更新する取引を避ける。新コマンドのID・互換性はこの方針の合意後に決める。

Q2とQ9の関係: 左右同時指令が有効なら左右の期限を同時に更新する。いずれかの値が不正なら両方を不採用とし、期限も更新しない。左右別々の取引に戻すことはしない。

第4ラウンド（Q10〜Q13はユーザー合意済み。未実装）:

- Q10: ESP32とSTM32は対応する新ファームを両方更新する運用とする。旧形式の速度指令で走行する互換経路を残さず、旧ファームとの混在では走行を許可しない。停止・緊急停止命令は引き続き受理する。
- Q11: 走行指令のACK欠落・NACK・不正応答を1回検出したら、ESP32も両輪停止を要求して再開待ちへ移る。STM32の250 ms期限は停止要求自体が届かない場合にも適用する。停止確認前は表示・ログで停止完了と扱わない。
- Q12: WebでSTM32が報告した走行許可状態・停止理由を表示する。状態を受信できない場合は「通信不明」と表示し、最後の状態を現在の確定状態として扱わない。表示追加によって停止処理を待たせない。
- Q13: センサー応答はVersion 2・32 byteを維持し、完成したスナップショットだけを公開する。既存の群別有効期限（加速度/ジャイロ250 ms、地磁気250 ms、温度/気圧1000 ms）を仕様へ明記する。群別取得時刻の追加は今回の安全改善には含めない。

追加の事実調査: 左右別値の同時指令・走行許可は未実装。`CMD_STATUS_REQ(0x10)` / `CMD_STATUS_RESP(0x90)` は定義済みだが、STM32のSPIで状態照会を処理する実装はない。現行WebのAPIはセンサー情報であり、走行許可・停止理由を公開していない。

- 同時指令: STM32 `Core/Src/spi_comm.c:208–230` の両輪指定は同じ方向・速度を適用する。関連ESP32 `src/main.cpp:332–333` は左右を別送信している。
- 状態照会: `Core/Inc/config.h:48–62` にIDがあるが、`Core/Src/spi_comm.c:302–309,323–357` のSPI処理に含まれない。
- ペイロード: `Core/Inc/packet.h:8–11` で最大32 byte。センサー形式は既に全32 byteを使用する。
- 応答判定: 関連ESP32 `src/main.cpp:73,268,324` は走行・停止送信の戻り値を未確認。`src/spi_comm.cpp:120–123` はACK/NACK以外の有効パケットも `SPI_RESULT_ACK` として扱う。走行指令では元CMDが一致するACKだけを成功とする必要がある。
- Web: 関連ESP32 `src/sensor_web_server.cpp:363–375` は走行状態・停止理由を公開していない。

回路の型番・保存先は未入手。Q15により、回路情報と実機確認は実機走行前の確認事項として残すことに合意した。

第5ラウンド（Q14・Q15はユーザー合意済み。改善仕様の最終合意済み）:

- Q14: PS3切断を検出した時も、通常の500 ms減速ではなく、両輪の駆動出力をゼロにして再開待ちへ移る停止要求を送る。ヘッドライトも消灯要求を送る。SPIで要求が届かない場合は、STM32の指令期限で停止する。□の緊急停止と異なり、再接続後は中立300 ms＋STARTで走行を再許可できる。
- Q15: 回路の型番・真理値表の確認と、制動特性・停止距離の実機試験を、実機走行の前提条件として残す。現時点で「ブレーキが効く」「車体が260 ms以内に止まる」とは確定しない。これらの未確認事項を明記した改善仕様として、今回の仕様調査をまとめる。

合意済みの仕様、受入条件、実機走行前の確認事項は [安全制御の改善仕様](safety_improvement_spec.md) に整理した。

## 判断後の検証候補

- 走行指令中にSPIを切断し、定義した期限内の出力停止を確認する。
- センサー要求だけを続けても、モーター指令の期限が延びないことを確認する。
- センサー切断・復帰中のPWM更新間隔とSPI応答を計測する。
- 起動中のコマンド、通常停止、反転途中の停止、緊急停止後の速度指令を確認する。
- センサー更新途中の要求でも、値・状態・時刻が同じ公開単位に属することを確認する。

優先順位とQ2〜Q15は合意済み。現行仕様の調査、改善候補の整理、改善仕様の合意を完了した。通信断停止の責務と復旧方針は [ADR 0001](adr/0001-motor-command-expiry.md) に記録した。ファームウェアは未変更、実機未検証。

追加の判断は推奨案と理由を記録して進め、後でユーザーが確認する方針も合意済み。未確認の回路特性・実測値を確認済みとして扱わない。
